A few ideas show up everywhere in this API. Read this once and the rest of the docs will read faster.

## Tenancy: you, your agencies, your agents

Your Athos account is a single **tenant** (a "reseller"). Everything you create — agencies, agents,
calls, scores, usage — belongs to your tenant, and the API only ever returns your tenant's data.
Your API key **is** the tenant boundary.

Within your tenant, Athos keeps a **roster**:

- An **agency** is one of your customers — a group of reps. It is created for you the first time
  you register a rep without naming one, and you can rename it.
- An **agent** is a rep. Each agent belongs to exactly one agency and is registered once per tenant,
  with at least one of their NPN, their email or **your own id for them** (`platformAgentId`) — and
  is findable afterwards by any of those or by the Athos id registration returns (`agentId`).

See [Managing agencies and agents](/backend/managing-agencies-and-agents). Nobody from your world
ever logs into Athos — the roster is maintained entirely through this API. The roster exists so
that every call can be attributed to one rep and one agency and **read back by agency and by rep**:
`GET /v1/calls?agencyId=` and `GET /v1/calls?agentId=` return practice and real calls together. A
rep must be registered before their first roleplay: a session token is only minted for a registered
agent, by its `platformAgentId` or its Athos `agentId`.

Every call and every `call.scored` delivery carries **two id families** for the same rep and
agency — one of each, never one value under two names:

- **Ours — `agentId` / `agencyId`** (and `callId`): the Athos ids registration returned. Always
  present. These are what you pass back: `?agentId=` / `?agencyId=` on `GET /v1/calls`,
  `agentId` on the mint, `{agencyId}` on `PATCH /v1/agencies`.
- **Yours — `externalUserId` / `externalAgencyId`**: the `platformAgentId` / `platformAgencyId` you
  registered, echoed back. `externalUserId` is `null` if you never registered one — join on
  `agentId` in that case; `externalAgencyId` is `null` likewise. On the wire you send them as
  `platformAgentId` / `platformAgencyId` (registration, the mint, `GET /v1/agents`) and read them as
  `externalUserId` / `externalAgencyId` (calls, deliveries, and the two `GET /v1/calls` filters of
  the same name). A field never holds the other family's value.

<Callout type="warn">
  Scoping by `agencyId` or `agentId` is checked against **your** roster (someone else's id is a
  `404`), but that is tenant isolation, not per-agency access control: anyone with your API key can
  read every call in your tenant regardless of agency. If you run a multi-agency product, enforce
  per-agency access **in your own backend**.
</Callout>

## Identifiers

| Id | Looks like | What it is |
| --- | --- | --- |
| **`agencyId`** | `athos_agency_V1StGXR8…` | The stable, public id for one of your agencies. Returned at registration; use it for `PATCH /v1/agencies/:id`, to register further agents into it, and to list its calls with `GET /v1/calls?agencyId=`. |
| **`agentId`** | `athos_agent_bR4kQ2wZ…` | The stable, public id for a rep. Returned at registration; look the rep up by it with `GET /v1/agents?agentId=`, mint with it, and list their calls with `GET /v1/calls?agentId=`. |
| **`callId`** | `athos_call_GZ1DjOkZv_…` | The stable, public id for a call. Use it for `GET /v1/calls/:id`, in webhooks, and in the SDK `ended` event. **This is the only call id that crosses the API boundary.** |
| **`requestId`** | `req_2f8c1e94-…` | Returned on every API response as the `X-Athos-Request-Id` header. Quote it in support tickets. |

You'll never see an internal database id. All four are opaque, semver-stable public contracts: a
resource returns its own id as `id`, and refers to another resource as `<resource>Id` (an agent's
`agencyId`, for example).

## The call lifecycle

```text
  created ──▶ live (rep + AI persona talk) ──▶ ended ──▶ scoring
                                                              │
                            ┌─────────────────────────────────┴───┐
                            ▼                                     ▼
                         scored                              not scored
                            │                                     │
                ┌───────────┴───────────────┐                     ▼
                ▼                           ▼       call.scored (success: false)
   call.scored (success: true)     GET /v1/calls[/:id]
```

Every call that ends reaches one of two terminal outcomes, and the `call.scored` webhook fires for
both: `success: true` when Athos scored the call, `success: false` when it could not be scored (the
rep never spoke, the call never completed, or scoring failed). **Only scored calls are readable over
REST** — a `success: false` call answers `404 CALL_NOT_FOUND` and never appears in `GET /v1/calls`,
so the webhook is the only signal you get for it. Handle both branches: see [when `success` is
`false`](/backend/webhooks#when-success-is-false).

`GET /v1/calls` returns scored calls only — it is a manager-history read, not a queue of
in-progress calls. The webhook is your notification for both sources; `GET /v1/calls` is the
history and reconciliation read.

## Call sources

Every call carries a **`source`**:

- **`roleplay`** — a practice call your rep ran through the SDK.
- **`ingestion`** — a real call one of your agencies' reps made on their dialer, ingested and scored
  by Athos once that agency has been switched on. See
  [Real-call analysis](/backend/real-call-analysis).

Both kinds fire the same `call.scored` webhook, carry the same ids, and are read from the same
endpoints — one `GET /v1/calls?agencyId=` page holds an agency's practice and real calls together,
newest first. A real call has no `drillKey`.
